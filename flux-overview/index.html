Flux + MFlux: Platform Overview

Nicolas Ventures — AI agent infrastructure

The Vision

Nicolas Ventures has an idea for a new venture on Monday morning. By Tuesday, it's a working business — website infrastructure provisioned, HR policies generated and filed, tax entity created, Shopify storefront configured, payment processing live, domain registered, DNS pointed. Not a plan. Not a proposal deck. A running business, built by AI agents that know how to stand up real infrastructure and get out of the way.

That's what this platform is for. Not one agent doing one trick — a fleet of specialized services that handle identity, secrets, storage, approvals, cost tracking, and deployment, all coordinated through a shared capability layer. The same platform that spins up a webhook relay today can spin up a business tomorrow. The services are different. The plumbing is the same.

Here's what that looks like in practice. I wanted to show off to my wife — build a custom Amazon Alexa skill for an integrated to-do list. It took six minutes. That included secrets management, structured logging on the shared log platform (this logging was used to troubleshoot), performance monitoring (we made it faster), authentication (three of those minutes were just navigating Alexa's own GUI to link the skill...I hate services not having APIs!). Pushing the finished service to GitHub. Nine minutes from nothing to a deployed, secured, logged, ready-to-use voice skill, that was integrated into a personal todo list (because everyone has to create their own todo app) — all because the platform already handles the hard parts.

What Problem Does This Solve?

Building AI-powered services usually means rewriting the same infrastructure every time — secrets management, logging, storage, retry logic, cost tracking. Each service ends up tightly coupled to a specific cloud provider, and swapping anything means rewriting everything.

Flux solves this with a capability layer. Services declare what they need ("store this," "fetch that secret," "log this event") and the platform handles how. Switch from local SQLite to Google Cloud Firestore to Graphiti graph database (Really good for tiered memory) by changing one config file. The service code doesn't change. At all.

MFlux sits above Flux and asks a harder question: what if AI agents could compete to build the best implementation of a service, and the platform could score them automatically?

What if we could “Grow our apps”? I want a rose that's a different color...a different shape...what if we develop software the same way?

Goals

  1. Write services once, run them anywhere. 12 capabilities (secrets, storage, logging, identity, cost tracking, approvals, etc.) with swappable connectors. Two profiles today: local (SQLite + filesystem) and GCP (Firestore + GCS + Secret Manager + Cloud Logging). Adding a new backend means writing one connector file, not touching service code.
  2. Automate quality judgment. The evolution engine scores AI-generated code on three axes: functional tests (does it work?), principle adherence (is it well-architected?), and scar tissue checks (did it avoid known pitfalls?). A second LLM acts as the principle judge, reading source code and scoring against 10 architectural rules.
  3. Make the platform self-improving. Competitions produce winners. Winners become the baseline for the next generation. The platform evolves by selection pressure, not manual refactoring.

The 10 Principles

Every Flux service is evaluated against these:

#PrincipleWhat It Means
1IdentitySecrets via Secret Manager through neutral wrappers. Never hardcoded.
2InfrastructureServerless compute (Cloud Functions or Cloud Run).
3CommunicationExponential backoff + timeouts on all external calls.
4LogicProvider-agnostic function signatures. No raw cloud SDK in app code.
5MemoryState lives in managed storage (Firestore), not local files.
6PersistenceAtomic writes. No race conditions (e.g., double-approve prevention).
7ReflexivityStructured logging with a "why" field on every entry.
8SovereigntyHigh-risk actions require explicit human approval before execution.
9DiscoveryEvery service registered in an inventory. Gateway auto-discovers.
10TemporalityDry-run mode: evaluate decisions without side effects.

These aren't aspirational. They're enforced — the evolution engine scores each one 0–2, and an agent that passes every functional test can still lose if it violates the principles. (Keep reading — this happened.)

How This Platform Can Grow

More connectors. AWS equivalents (DynamoDB for flux.db, S3 for flux.store, CloudWatch for flux.log) would be one connector file each. An Azure profile the same. Services wouldn't change.

More challenge specs. Each new YAML spec is a new competition. Any well-specified service can become a challenge — rate-limiter, notification fanout, data pipelines, ML inference wrappers.

Multi-generation evolution. Today the engine runs single-generation competitions. The architecture supports breeding (combine the best genome traits), mutation, and multi-generation loops. Winners from generation 0 seed generation 1.

Cross-model competitions. Agents can be backed by different LLMs — Claude, GPT, Gemini. Scoring is model-agnostic. Early runs suggest model choice matters less than seed quality.

Fleet management. MFlux already manages multiple Flux instances with separate identities, secrets, and budgets. Scaling from 2 to 20 is infrastructure, not architecture.

Agent swarms. The capability layer doesn't care who's calling it — a human, a single agent, or fifty agents working in parallel. Because every service already has identity, secrets, logging, approvals, and cost tracking baked in, you can point a swarm of agents at a problem and the platform handles coordination naturally. Each agent gets its own identity, its own budget ceiling, its own audit trail. High-risk actions still require human approval regardless of which agent initiated them. The evolution engine is already a proof of concept: four agents building competing implementations simultaneously, scored automatically, no human in the loop until the results are in. Extending that pattern to runtime — agents collaborating on a task, dividing work, merging results — is plumbing, not architecture.

Ontology layer. Built from the start as a platform that could support an ontological layer — typed objects with links, properties, and actions spanning all services — this is the next major capability on the roadmap. Adding it unlocks cross-service context (an agent can trace a Rook task back to the webhook event that triggered it), data-driven session briefings from live system state instead of static memory files, and automated cross-service rules that today require manual wiring. The capability layer makes this a thin addition — one more Cloud Function, same connectors underneath.

Interesting Use Cases

AI agent code review. The principle judge already reads source code and scores it against architectural rules — design intent, not just syntax.

Self-healing services. Service fails health check? Trigger an evolution run. The engine generates a new implementation from the spec, tests it, deploys the winner.

Spec-driven development. Write a YAML spec. Hand it to the evolution engine. Get back a deployed, tested, scored implementation. Skip the boilerplate phase.

Multi-cloud migration. Write connectors for AWS/Azure. Run the same services on both. Compare costs and reliability empirically — it's a config change, not a rewrite.

Personal AI infrastructure. This is what Flux already is — Telegram messages, GitHub webhooks, domain brainstorming, task management, and content generation all flowing through one system with shared identity, logging, and cost tracking. One person, 23 services, $17. No need for OpenClaw, no need for n8n, no need for Zapier. I just built my own — tailored to exactly how I work, integrated with exactly the services I use, and it just works. That's the point: the capability layer makes building your own agent infrastructure faster than configuring someone else's.

Emergent API combinations. There's an explosion of useful API services happening right now, and it's moving too fast for any human to track. RunPod.io for ephemeral GPUs at near-zero cost (I used Google's GemmaMed specialized model that can read EPIC healthcare records with amazing results...all private). Cloudflare Durable Objects — persistent, stateful containers that give agent swarms long-lived sessions and open up combinations that weren't possible with stateless functions alone. Web-to-markdown services that let agents read any website cleanly without headless browser automation. New agent-native APIs are launching constantly, many designed specifically for machine consumption rather than human UIs. We keep discovering services we didn't know existed a few weeks ago that solve problems we were overengineering around. The platform makes this compounding instead of chaotic — every new connector (Cloudflare, AWS, Azure, HubSpot, and hundreds more) plugs into the same capability layer, and agents that understand the full library start composing services in ways you wouldn't think of. A human building sequentially picks the tools they know. An agent with access to the full catalog finds combinations the human would miss.

Agent-native payments. Add stablecoin wallets and protocols like x402 for machine-to-machine payments, and agents stop needing a human to authorize every transaction. Microtransactions become native — an agent can pay for a GPU burst on RunPod, purchase a domain, top up an API quota, or settle a service fee, all within the platform's existing approval and budget framework. Low-value transactions execute automatically; high-value ones still route through human sovereignty. The plumbing for cost tracking and budget ceilings is already there.

The Evolution Engine in Action

This is the part where AI agents compete head-to-head.

The Challenge

Agents build an "approval-relay" — a serverless GCP service that receives action requests, risk-assesses them, executes low-risk ones immediately, and queues high-risk ones for human approval. Two endpoints, Firestore state, secrets via neutral-intent wrappers, structured logging, dry-run mode. All 10 principles exercised.

Here's the trimmed spec each agent receives:

name: approval-relay
version: "2.0"

challenge:
  summary: |
    Build and deploy a serverless GCP service called "approval-relay" that receives
    action requests, assesses their risk level, executes low-risk actions immediately,
    and queues high-risk actions for explicit approval. A separate /resolve endpoint
    approves or rejects pending actions. All external interactions MUST use neutral-intent
    wrappers. Must support dry_run mode.

  flow: |
    POST /action — Submit an action request
    1. Validate: reject 400 if action/target/source missing
    2. Assess risk:
       - LOW:  action="notify" OR (action="transfer" AND amount <= 100)
       - HIGH: action="delete" OR (action="transfer" AND amount > 100)
    3a. LOW-RISK: fetch secret -> POST httpbin.org -> write Firestore -> return 200
    3b. HIGH-RISK: write to pending-approvals -> return 202

    POST /resolve — Approve or reject a pending action
    1. Fetch pending approval from Firestore
    2. If approved: execute the original action
    3. If rejected: mark rejected, done
    4. Double-approve returns 409

  neutral_intent_requirement: |
    ALL instances must provide language-appropriate neutral-intent wrappers:
    - fetch_secret(secret_name)
    - retry_with_backoff(callable, ...)
    - create_logger()
    Direct use of raw cloud SDK secret clients is a disqualifier.

19 automated test cases, weighted by importance. The big ones (5 points each): low-risk execute, high-risk pending, approve pending. The principle judge (Gemini Flash) then reads the source code and scores 0–2 on each of the 10 principles. Scar tissue checks look for things like missing timeouts, hardcoded secrets, plain text errors.

The Seeds (What Makes Agents Different)

Each agent starts from a "seed" — a genome describing the platform's language, architecture, and lessons learned. Here are two that competed head-to-head:

flux-001 (Python, shared library)

## Architectural Style
- Shared library: All cloud operations go through lib/caf_helpers neutral intents.
  Import fetch_secret, create_logger, retry_with_backoff from lib.caf_helpers.
  Never use raw google.cloud.* in application code.
- Structured logging: Use create_logger() from caf_helpers. Every log entry
  needs a "why" field explaining the human-readable reason.
- Deploy pipeline: ./tools/deploy.sh services/<name> handles gen2 flags,
  AST-based entry-point detection, lib/ staging, smoke test, and registry update.

flux-005-rapidpulse (TypeScript, dependency injection)

## Architectural Style
- Language: TypeScript (Node.js 20 runtime)
- File structure:
  - services/<name>/src/index.ts (function handler)
  - services/<name>/src/core/ (business logic)
  - services/<name>/src/neutral/ (interfaces + intent types)
  - services/<name>/src/adapters/gcp/ (Secret Manager, Firestore, Storage)
- Import patterns:
  - src/index.ts wires adapters into core (dependency injection).
  - src/core/ imports only from src/neutral/ (interfaces, never implementations).
  - No @google-cloud/* imports anywhere except src/adapters/gcp/*.ts.

Same challenge, totally different starting points. Python with a shared library you import from. TypeScript with hexagonal architecture and dependency injection. The question: does it matter?

Agent-3 (TypeScript/RapidPulse) passed 61 out of 63 tests. It built a working service. It handled risk assessment, approval queues, dry-run mode, Firestore writes, double-approve prevention — all of it. So what happened? Agent-1's genome says: "Import fetch_secret, create_logger, retry_with_backoff from lib.caf_helpers. Never use raw google.cloud.*." That's a direct instruction. The agent followed it.

Agent-3's genome prescribed src/neutral/ interfaces, src/adapters/gcp/ implementations, dependency injection at the handler level. Architecturally sophisticated. But the LLM agent couldn't wire it up correctly. The principle judge saw raw SDK usage and scored zeros across the board.

The takeaway: "Import these three functions" beat "implement this hexagonal pattern" because the LLM could follow one instruction literally and couldn't reliably construct the other from a description.
